# 구매 전 고정 질문과 AI 변환

> 아래 문항 목록은 유지하지만 서버 저장 흐름은 이전 `ADAPTIVE` 모드용입니다. 신규 기본값은 `LOCAL`이고 질문·답변은 기기에만 저장합니다. 새 경로와 종료 시 AI 요약은 [handoff 연동 계약](handoff-integration.md)을 따르세요.

두 번째 질문 이미지의 14개 문항을 `pre-v1` 고정 목록으로 반영했습니다. 구매 후 15개 문항과 별도 목록입니다. AI는 서버가 허용한 후보 중 하나를 선택하고 품목에 맞게 문장을 바꿉니다. 질문 코드, 답변 의미, 입력 형식, 금액과 기간은 서버가 정합니다.

## 질문 목록과 입력

| 주제 | 질문 코드 | 답변 |
|---|---|---|
| 트리거 | `DISCOVERY` 알게 된 경로 | 광고 / SNS·유튜버 / 친구 / 직접 검색 / 기타 |
| 트리거 | `CURRENT_MOOD` 현재 기분 | 스트레스 / 심심함 / 기분 좋음 / 평소와 같음 |
| 트리거 | `DISCOUNT_PRESSURE` 할인·한정 압박과 정가 구매 의사 | 두 조건을 함께 표현한 선택지 |
| 필요성 | `RECENT_NEED` 최근 불편 | 네 / 아니요 / 모름 |
| 필요성 | `ALTERNATIVES` 기존 물건으로 대체 | 비슷한 물건 없음 / 대체 가능 / 대체 어려움 / 모름 |
| 필요성 | `PROBLEM_TO_SOLVE` 해결할 문제 | 한 문장, 최대 300자 또는 모름 |
| 사용 예측 | `FIRST_USE` 처음 쓸 시점·상황 | `when` + `context` 두 객관식 값 |
| 사용 예측 | `EXPECTED_USE_DAYS` 예상 사용일수 | 구매 후 30일 중 0~30일 또는 모름 |
| 가치·기회비용 | `CASH_CHOICE` 현금으로 받아도 구매할지 | 구매 / 현금 보유 / 모름 |
| 가치·기회비용 | `WORK_VALUE` 근로 시간 대비 가치 | 가치 있음 / 없음 / 모름 |
| 가치·기회비용 | `GOAL_DELAY` 목표가 늦어져도 구매할지 | 네 / 아니요 / 모름 |
| 지속성 | `WANTED_WEEK_AGO` 일주일 전에도 원했는지 | 네 / 아니요 / 모름 |
| 지속성 | `SHOW_TO` 먼저 보여주고 싶은 대상 | 본인 / 가족·연인 / 친구 / SNS / 보여줄 생각 없음 / 모름 |
| 지속성 | `REPLACE_IF_LOST` 분실하면 다시 구매할지 | 네 / 아니요 / 모름 |

사용자가 앞서 정한 단위에 따라 이미지의 ‘한 달에 몇 번’은 **구매 후 30일 동안 며칠**로 통일합니다. 같은 날 여러 번 쓰더라도 1일입니다. 고정 30일 전망이므로 등록 월이 28·29·31일인 것과 구분합니다. 예산의 하루 저축액은 계속 실제 월 일수로 계산합니다.

## 질문 선정과 고정

등록 다음 날부터 품목당 하루 하나를 묻습니다. 관찰 일차에 따라 트리거 → 필요성 → 사용 예측 → 가치 → 지속성 순서로 주제를 순환하고, 해당 주제에서 AI가 적합한 문항을 선택합니다. 같은 문항이 최근에 나왔다면 가능한 한 다른 후보를 제공합니다. 3일짜리 관찰에서 14문항 모두를 묻지는 않습니다.

마지막 관찰일에 숫자로 답한 사용일수 예측이 없다면 `EXPECTED_USE_DAYS`를 우선합니다. AI는 이 경우 해당 문항을 품목에 맞게 바꾸며 다른 문항으로 대체하지 못합니다. 그래도 모름으로 답하거나 빠뜨리면 사용일수는 `null`이며 임의로 만들지 않습니다. 보류 연장의 공백은 관찰 일차에 넣지 않습니다.

생성 요청을 다시 보내도 같은 시뮬레이션·서울 날짜에는 같은 질문을 반환합니다. 생성 도중 구매가 확정되면 뒤늦게 구매 전 질문을 저장하지 않습니다. 구매·포기 이후에는 구매 전 답변을 수정할 수 없습니다.

AI 오류·시간 초과에는 품목명이 들어간 고정 템플릿으로 대체합니다. 형식 오류·금지 코드·사용 횟수/다른 기간으로 바뀐 예측은 한 번 보정 요청하고 실패하면 대체합니다. 질문 버전, 원본 문구, 실제 문장, 선택지와 생성 당시 정보를 함께 저장합니다.

## API

공통 접두사는 `/api/v1`입니다.

| 동작 | 요청 |
|---|---|
| 구매 전 원본 질문 목록 | `GET /pre-purchase-question-templates` |
| 오늘 질문 생성·재사용 | `POST /simulations/{simulation_id}/daily-question` |
| 답변 작성·수정 | `PUT /simulation-questions/{question_id}/answer` |
| 단일 질문·답변 조회 | `GET /simulation-questions/{question_id}` |
| 날짜별 이력·최신 예측 | `GET /simulations/{simulation_id}/questions?limit=30&offset=0` |
| 종료 결과 | `GET /simulations/{simulation_id}/result` |

신규 `question_mode` 기본값은 `LOCAL`입니다. 아래 `ADAPTIVE` 요청은 이전 서버 저장 방식을 명시적으로 선택하는 호환 계약입니다. 기존 자료와 이전 Android를 위한 `LEGACY`도 명시적으로 지원하며, 방식별 답변을 같은 시뮬레이션에 혼합하지 않습니다. 과거 `v1` 시뮬레이션은 마이그레이션으로 변환하지 않습니다.

새 Android는 `/today` 또는 `/home.today`의 `pre_purchase_questions`를 사용합니다. 품목·카테고리·일차·기간이 있으며 `question:null`이면 `generate_url`에 POST합니다. `GET`이나 푸시 워커는 AI를 호출하지 않습니다. 생성된 `question`, `reference_text`, `answer_spec`으로 화면을 구성합니다. 초안의 `supplemental_question`은 새 흐름의 고정 질문을 대체하지 않습니다.

완료 카드는 `pre_purchase_answered`로 이동하고 `?include_answered=true`로 다시 볼 수 있습니다. `summary.answered_count/remaining_count`는 구매 전 두 방식의 합계입니다. 기존 `summary.counts`의 YES/NO/UNSURE 집계는 LEGACY 전용이며 새 기분·가치 답변을 여기에 섞지 않습니다. 구매 후 질문은 별도 `purchase_questions/purchase_answered`입니다.

### 답변 예시

해당 질문의 형식에 맞는 필드 **하나만** 보냅니다. 입력 범위와 코드 목록은 생성된 `answer_spec`이 기준입니다.

```json
{"choice_code":"STRESS"}
```

```json
{"number_value":15}
```

```json
{"text_value":"걷는 동안 발이 아파서 편하게 이동하고 싶어요."}
```

```json
{"object_value":{"when":"THIS_WEEK","context":"EXERCISE"}}
```

오늘 답변은 수정 가능하고 과거 날짜는 조회만 가능합니다. 같은 답변을 다시 보내거나 수정해도 답변 행은 하나입니다. 다른 게스트의 질문·이력에는 접근할 수 없습니다. 신규 흐름에 옛 `/simulations/{id}/answers/{date}`를 호출하면 `409 ADAPTIVE_QUESTION_REQUIRED`입니다.

## 금액과 근로 시간

`PUT /budgets/{month}`에 선택적인 `hourly_wage`를 추가했습니다. 원 단위 양수이며, 값을 모르면 생략하거나 `null`로 둡니다. 수입이나 법정 최저임금으로 시급을 추정하지 않습니다.

```json
{"income":1000000,"food":200000,"living":200000,"transport":100000,"savings":150000,"hourly_wage":10000}
```

`WORK_VALUE`는 등록 가격 ÷ 입력 시급을 약 두 자리 소수 시간으로 표시합니다. `GOAL_DELAY`는 기존 계획 저축액 기준의 지연 일수를 사용합니다. 시급이 없으면 근로 시간 질문, 목표·계획 저축이 없으면 목표 지연 질문을 후보에서 제외합니다. 금액·시간·지연 설명은 AI가 아닌 서버의 `reference_text`에 들어갑니다. 생성 후 예산을 바꿔도 해당 질문의 설명은 바뀌지 않습니다.

## 결과와 구매 후 비교

새 흐름의 사용일수는 `EXPECTED_USE_DAYS`에 직접 답한 값만 사용합니다. 필요성의 YES, 좋은 기분, 구매 욕구, 추천, 과시 대상은 사용일수가 아닙니다. 미응답·모름을 0일로 바꾸지 않습니다.

- `question_mode=ADAPTIVE`, `prediction_window_days=30`을 확인해 결과를 표시합니다.
- `duration_days`는 관찰 기간 3/7/14일(연장 포함), `expected_used_days`는 **구매 후 30일 예상 사용일수**입니다. 둘을 합쳐 ‘14일 중 15일 사용’이라고 표시하면 안 됩니다.
- 예상 사용률은 예상 일수 ÷ 30, 예상 사용일당 비용은 등록 가격 ÷ 예상 일수입니다. 0일이나 모름이면 비용은 `null`입니다.
- `unused_days=null`입니다. 이 다면 질문들은 사용하지 않은 날을 직접 관찰한 기록이 아닙니다.
- 비교는 정상 종료·확정 응답 70% 이상·숫자 예측 존재가 모두 필요합니다. 조기 구매는 부분 관찰로 남고 수치 비교에서는 제외합니다. 모름을 포함한 시점·상황 답변도 확정 응답 수에서는 제외합니다.

`BUY` 때 `purchases.pre_purchase_snapshot`에 당시 예측·시점/상황·해결할 문제·원본 질문과 답변을 고정합니다. 구매일을 과거로 기록하면 그 날짜 이후 답변은 구매 전 예측에 넣지 않습니다. 이후에는 과거 질문이 바뀌거나 새 모델을 사용하더라도 당시 답변을 기준으로 비교합니다.

- 구매 후 7일 사용 점검: `(예상 30일 사용일수 ÷ 30) × 7`과 실제 0~7일을 비교합니다.
- 사용 상황 점검: 구매 전 `FIRST_USE.context`와 실제 상황 코드를 비교합니다. 첫 사용 시점과 일반적인 사용 상황은 서로 다른 값이므로 시점 일치까지 추정하지 않습니다.
- 필요 해결 회고: 저장된 `PROBLEM_TO_SOLVE` 문장을 그대로 참조합니다. 문장이 없으면 기존 구매 이유를 참조합니다.
- 자유 입력은 사용자 데이터로 취급하며 모델이나 서버에 대한 명령으로 실행하지 않습니다.

## 배포와 호환

`alembic upgrade head`로 `0004_pre_purchase_questions`를 적용한 뒤 API·워커를 함께 재시작합니다. 기존 사용일수·질문·구매·리포트 기록은 보존됩니다. 새 시급은 `null`, 과거 구매의 별도 예측 스냅샷도 `null`이며 이전 방식의 계산을 계속 사용할 수 있습니다.

새 질문·답변·시급·구매 스냅샷 데이터가 있는 DB의 다운그레이드는 자동 삭제를 막기 위해 거부합니다. 백업 복구나 후속 마이그레이션을 사용합니다. 기존 Android가 새 질문 API를 연결하기 전에는 등록에 `question_mode:LEGACY`를 명시해야 합니다.

Lablup 대역으로 후보 선택·잘못된 단위·시간 초과·중복 요청·구매 확정 중 생성·구매 전후 비교를 검증합니다. 실제 모델의 문장 품질은 API 키가 연결된 환경에서 추가 확인이 필요합니다.
