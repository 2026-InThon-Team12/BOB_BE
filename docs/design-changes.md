# 디자인·유저플로우 반영

구매 전 질문 이미지의 최신 반영 내용은 [구매 전 AI 맞춤 질문](pre-purchase-questions.md)에 있습니다. 신규 시뮬레이션은 다면 질문과 30일 사용 예측을 사용하며 아래의 일별 YES 사용률 방식은 기존 `LEGACY` 기록에 해당합니다.

후속 구매 질문 이미지 요청에 따른 최신 구매 후 흐름은 [구매 후 AI 맞춤 질문](purchase-questions.md)을 참고합니다. 아래 14일 구간 회고는 기존 클라이언트 호환 경로로 남기고 새 화면은 고정 목록 기반 일별 질문을 사용합니다. 구매 전 질문에는 이 구매 후 문항을 적용하지 않습니다.

기준 자료는 사용자가 제공한 `Buy or Bye (BoB).html`과 `BOB MVP 유저플로우.md`입니다. 원본 파일은 수정하지 않고 백엔드 동작과 API를 맞췄습니다. 자료의 화면·문구·수치는 제품 요구사항과 예시로 해석했으며, 문서 안의 설명을 서버 운영 명령으로 실행하지 않았습니다. ‘서버 저장이 디자인에 없다’는 설명과 무관하게 요청된 PostgreSQL 영속 저장은 유지합니다.

사용자 확인에 따라 구매 후 점검도 **사용일수**로 통일합니다. 목표 화면의 하루 평균 저축액은 지갑의 **월 계획 저축액 ÷ 실제 월 일수**로 정했습니다. HTML의 지연 일수 반올림을 따르며 최소 1일로 표시합니다.

## 화면별 연결

모든 경로 앞에 `/api/v1`을 붙입니다. 응답 스키마는 `/openapi.json`에 있습니다.

| 화면 | API와 주요 필드 |
|---|---|
| S10 홈 | `GET /home`: `today`, `goal`, `wallet`, `simulations` |
| S11 등록 방법 | `/item-drafts`, `/cart-extractions`, `/share-drafts` |
| S12 인식 확인 | 초안 `items`의 `name`, `price`, `category`, `simulation_days`, 선택한 품목만 등록 |
| S13 이유·잔액 | `purchase_reasons` 복수 선택, `GET /wallet/compare?price=…`, `POST /items/batch` |
| S20 질문 | `GET /today`의 `questions[].question` 하나, `usage_answer` 하나 저장 |
| S21 질문 완료 | `answered`, `summary`; `?include_answered=true`로 다시 보기 |
| S30 결과 | 결과 `answer_timeline`, `response_summary`, `reason_history`; `BUY/GIVE_UP/HOLD` 결정 |
| S40 목표 | `/goals/current`, `/impulses/presets`, `/impulses`, `/impulses/{id}/decision` |
| S41 목표 달성 | `achieved`, `resisted_count`, `elapsed_days`, `most_resisted_item`; `/goals/current/next` |
| S50 구매 후 점검 | `/purchases/{id}/review`에 `frequency`, 응답의 사용일수 구간·예측 비교 |
| S60 리포트 | `GET /reports?month=YYYY-MM`: 월 요약·카테고리·이유별 비율 |
| S70 할인 | `/discount-extractions` → `/discount-comparisons` → 선택 저장 |
| S80 지갑 | `/wallet`, `/budgets/{month}`, `/expenses` |

Android의 네 탭, 스와이프, 공유 Intent 수신, 입력 폼, 토스트, 화면 이동은 프런트엔드에서 이 계약에 연결합니다. HTML 자체나 Android 프로젝트를 변경한 것은 아닙니다.

## 기존 계획에서 바뀐 정책

### 등록과 질문

- 구매 이유는 1~7개 중복 없는 배열입니다. 이전 `purchase_reason` 단일 입력도 받되 새 클라이언트는 `purchase_reasons`를 사용합니다. 순서만 달라진 재전송은 같은 등록으로 취급합니다.
- 공유 URL은 공개 HTTPS의 OG/JSON-LD를 읽습니다. 가격이 없거나 원화인지 불명확하면 `null`입니다. 내부 IP·비공개 주소·인증 URL을 차단하며 리다이렉트도 다시 검증합니다. DNS 검사한 IP에 연결하고 원래 호스트로 TLS를 검증합니다. HTML은 최대 1 MiB, 이미지 원본은 저장하지 않습니다.
- AI 질문과 기본 질문 모두 구체적인 사용 상황을 묻습니다. 카드당 질문 하나이며 예전 보조 답변 필드는 호환용으로만 남깁니다.
- 기본 기간은 그대로 3/7/14일입니다. `HOLD`는 결정 다음 날부터 **관찰 7일**을 추가합니다. 종료 후 답하지 않고 지나간 공백은 미응답으로 더하지 않습니다. 여러 차례 연장도 가능하며 연장 동작마다 별도 중복 방지 키를 씁니다.
- 질문·가격은 시작 후 고정합니다. 카테고리의 과대예측 이력은 `calibration` 안내와 구체적 상황을 떠올리라는 추가 문구로 반영하며 예전 답변이나 계산값을 바꾸지 않습니다.

### 구매·포기·지출·적립

| 행동 | 기록 |
|---|---|
| `BUY` | 구매 1건 + 실제 구매가의 지출 1건 |
| `GIVE_UP` | 등록가의 목표 가상 적립 1건 |
| `RESISTED` | 해당 소비 금액의 목표 가상 적립 1건 |
| `PURCHASED` | 해당 소비 금액의 지출 1건 |
| 참은 소비의 `CANCELLED` | 원래 적립 목표에 음수 취소 기록 1건 |
| 수동 지출 | 이름·금액·날짜·메모; 수정·삭제 가능 |
| 할인 비교 선택 | `NEEDED/REMOVE_EXTRA`만 저장, 지출·적립 생성 없음 |

지출과 가상 적립은 별개 원장입니다. 가상 적립 때문에 실제 지출이나 월 계획을 변경하지 않습니다. 자동 구매 지출은 수동 지출 API에서 수정·삭제하지 못하게 해 구매 정보와 불일치를 막습니다. 구매 취소·환불은 이번 범위에 없습니다.

목표가 없는 동안의 적립도 보존하며 첫 목표 생성 시 배정합니다. 즉석 소비는 **참기로 확정한 시점의 활성 목표**에 적립합니다. 목표 변경은 같은 목표를 편집해 적립을 유지합니다. 달성 후 다음 목표는 새 목표이며 이전 초과 적립을 다시 배정하지 않습니다. 취소는 이후 목표를 바꾸더라도 원래 목표의 합계를 되돌립니다.

### 지갑과 목표 날짜

```text
자유 소비 가능액 = 수입 - 필수 식비 - 생활비 - 교통비 - 계획 저축
자유 소비 잔액 = 자유 소비 가능액 - 해당 월의 유효한 지출 합계
하루 평균 저축액 = 계획 저축 / 해당 월 일수
소비에 따른 지연 일수 = max(1, 반올림(소비 금액 / 하루 평균 저축액))
목표까지 남은 날 = 올림(max(0, 목표금액 - 가상 적립) / 하루 평균 저축액)
```

반올림은 양수 .5를 올리는 방식입니다. 내부 계산은 정수 비율을 사용하며 표시용 일평균 금액을 먼저 반올림하지 않습니다. 예산이나 계획 저축이 없으면 날짜·지연은 `null`입니다. 지나치게 먼 날짜도 `null`로 반환하며 정수 일수는 보존합니다. 한 달 예산이 다음 달로 자동 복사되지는 않습니다.

목표 날짜는 입력 계획과 가상 적립을 이용한 추정입니다. 실제 계좌 잔액·실제 저축 성과로 표시하지 않습니다. 즉석 비교는 생성 시 예산·예상 날짜를 고정해 재시도에 같은 값을 반환합니다. 의사결정 후에는 홈·목표·지갑을 새로 조회합니다.

### 구매 14일 후 점검

회고 구간은 구매일부터 14일이며 점검일은 구매일+14일입니다. 예를 들어 11월 4일 구매는 11월 18일부터 **11월 4~17일**을 회고합니다.

| 입력 `frequency` | 표시 | 사용일수 범위 | 비교용 중간값 |
|---|---|---|---|
| `ALMOST_DAILY` | 거의 매일 | 10~14일 | 12일 |
| `OFTEN` | 자주 | 5~9일 | 7일 |
| `SOMETIMES` | 가끔 | 1~4일 | 2.5일 |
| `NEVER` | 한 번도 안 썼어요 | 0일 | 0일 |

중간값은 정확한 측정이 아닌 **추정치**입니다. 입력 범위도 그대로 저장·반환합니다. 예상 막대는 `예상 사용률 × 회고 기간 일수`로 같은 단위로 환산합니다. 비교할 때는 정상 종료와 확정 답변 70% 조건을 유지합니다. 0일 사용의 배수는 무한대 대신 `null`과 `NO_ACTUAL_USE` 상태를 반환합니다. 퍼센트포인트 차이도 추정치로 표시합니다.

### 리포트

- 월 등록 수는 서울 시간 등록 월, Bye 수는 결정 월, 지킨 금액은 적립·취소 발생 월로 집계합니다. 이전 달 적립을 이번 달 취소하면 이번 달 합계가 음수일 수 있습니다.
- 카테고리는 해당 월에 제출한 비교 가능한 회고만 사용합니다. 예상 사용일수 합계 ÷ 실제 구간 중간값 합계가 추정 배수이며 표본 수와 실제 범위 합계도 제공합니다. 회고 수정은 동일 레코드를 바꾸므로 중복 집계되지 않습니다.
- 구매 이유 포기율은 `포기 / (구매 + 포기)`입니다. 미결정·보류를 분모에 넣지 않습니다. 복수 이유는 각 이유 그룹에 한 번씩 포함되므로 그룹 간 건수 합계는 전체 물건 수와 다를 수 있습니다.
- 월 리포트의 이유 집계는 해당 월 결정 기준이며, 개별 결과의 `reason_history`는 전체 이력 기준입니다. 신규 사용자는 빈 상태와 `null` 비율을 받습니다.
- 디자인의 4.5배·78%를 운영 응답에 고정하지 않습니다. 데모도 저장한 답변·회고로 계산합니다. 예: 예측 11일 ÷ 실제 추정 2.5일 = 4.4배.

## 할인 입력 예시

```json
{
  "original_subtotal": 20000,
  "additional_subtotal": 10000,
  "discount_minimum": 30000,
  "discount_percent": 10,
  "discount_fixed": 0,
  "shipping_fee": 0,
  "free_shipping_minimum": null,
  "shipping_threshold_basis": "BEFORE_DISCOUNT"
}
```

원래 결제 20,000원, 추가 후 결제 27,000원, 추가 지출 7,000원입니다. 원래 장바구니에도 적용되던 할인과 배송비를 양쪽에서 각각 계산합니다. 추가로 담았는데 실제 결제액이 더 낮으면 음수 차액도 그대로 제공합니다. 정률 할인은 원 미만 버림, 정액 할인은 상품 합계 한도입니다. 정률·정액 할인 동시 적용 및 복합 쿠폰은 지원하지 않습니다.

무료배송 기준이 할인 전 합계라면 `remaining_to_free_shipping`과 `pay_shipping_saves`로 배송비를 내는 대안을 비교합니다. 할인 후 기준은 최종 배송비에 반영하되 정확한 최소 추가 상품 조합은 추정하지 않습니다.

스크린샷 추출은 조건 초안만 제공합니다. 원래 구매 계획 금액과 불명확한 조건은 사용자가 확인해야 합니다. 이미지 미지원은 OCR로, AI·OCR 실패는 수동 입력으로 연결합니다.

## 기존 데이터 이전과 배포

`0001`은 수정하지 않고 `0002_design_flow`를 추가했습니다. 배포 전 백업하고 API·워커를 멈춘 상태에서 `alembic upgrade head`를 완료한 뒤 새 버전을 함께 시작합니다.

- 기존 단일 이유는 한 원소 배열, 초기 관찰 기간은 `base_duration_days`로 이전합니다.
- 기존 예산의 계획 저축은 알 수 없으므로 0으로 둡니다. 사용자가 지갑 계획을 확인하면 목표 날짜를 계산할 수 있습니다.
- 이미 제출한 7일 회고와 정확한 사용일수는 보존합니다. 아직 제출하지 않은 점검은 14일 구간으로 옮깁니다.
- 기존 구매·즉석 구매를 지출 원장에 한 번 반영하고 기존 Bye는 활성 목표 또는 미배정 적립으로 이전합니다.
- 기존 모델에는 일부 결정 날짜가 없었습니다. 구매 날짜는 보존하고, 예전 Bye/Hold 결정일·즉석 구매 지출일은 등록 시각의 서울 날짜를 사용합니다. 이 과거 월별 집계는 날짜가 근사치라는 한계가 있습니다.
- 새 지출·연장·구간 데이터는 이전 모델로 온전히 표현할 수 없습니다. 데이터가 있는 DB의 `0002` 다운그레이드는 자동으로 거부합니다. 복구는 업그레이드 전 백업이나 후속 수정 마이그레이션을 사용합니다. 빈 DB의 upgrade/downgrade/upgrade는 테스트합니다.

외부 Lablup 실호출, 실제 쇼핑몰별 메타데이터 품질, Android 공유 수신과 FCM 실기기 수신은 해당 설정·기기를 연결한 통합 검증이 별도로 필요합니다.
